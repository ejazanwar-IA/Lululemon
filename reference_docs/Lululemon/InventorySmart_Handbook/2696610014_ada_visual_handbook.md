## Purpose

This document provides a comprehensive overview of the **ADA Visual** module within **Inventory Smart**. It details the key parameters displayed on the ADA Visual screen, explaining how changes made in the frontend affect backend processes and vice versa. Additionally, it outlines the calculations behind specific metrics, ensuring clarity on how each value is derived.

This guide serves as a quick reference for users onboarding or working with the ADA Visual module, helping them navigate its functionalities and understand system interactions.

# Adjusted Forecast Landing Screen : 

**For MFP enabled clients:** When the user clicks on “**Forecast Management**” at the top right of the “Forecast Overview” section on the MFP screen, they will be directed to the “Adjusted Forecast” landing page.

**For non MFP clients:** When the user clicks on the ADA Module from the InventorySmart tool, they will be directed to the “Adjusted Forecast” landing page. User can apply the filters from this screen to load the corresponding data.

## **1. "See Historic View" Dropdown**

* This dropdown allows users to view historical data based on the selected **aggregation level** (weeks, months, or quarters).
* Users can select a specific period to go back in time and see forecasted values for the chosen filters.
* **Impact of dropdown selection:**

    * Affects Actuals, Forecast, and MFP metrics.
    * If the user selects 6 weeks in the historic view, the tool will load the past 6 weeks of data as per the forecast refresh done on the past 6th week (snapshot week).
    * If the selected value is 4 weeks, then last 4 week of forecast metrics are loaded as per the refresh of past 4th week (snapshot week)
    * The historical data is fetched from `ADA_VISUAL_PREDICTIONS_HIST` table with the filter of `snapshot_week` and `fiscal_year_week`.
    * **Example:**
    
        * If `previous_week = 202443`, the 6th week in the past is `202438`.
        * Forecasts for **weeks 202438 to 202443** will be shown as per the forecast refresh done in the week of `202438` ( `snapshot_week = 202438`).
        
    
* For the historical view, user can go back till 8 weeks.
* User can not make any edits in the historical data view.

## **2. “Eligible SKUs” vs “All SKUs” Toggle**

**"All SKUs" Toggle** → Actuals, historic forecasts & MFP are based on historical Store-SKU Eligibility(SSE).

**"Eligible SKUs" Toggle** → Uses current & forward-looking SSEs. Only products eligible in both current & past weeks are considered for aggregation.

## **3. Drivers of Forecast (Update Process)**

### **3.1 ADA Visual Predictions Table**

* **Granularity:** Data is stored at the **Product-Store-Week-Scenario** level. (If there is specific requirement then the forecast can be maintained at **product-store-date-scenario** level)
* For each **product-store-week**, **20 scenarios** are maintained with an incremental gap of **5** starting from 0 till 95.

![](blob:https://media.staging.atl-paas.net/?type=file&localId=73ab0cc0-d9c2-47c2-b27f-3fee220bbd96&id=8e946a85-ec60-424a-9006-abfc0c35af5d&&collection=contentId-2696610014&height=445&occurrenceKey=null&width=1816&__contextId=null&__displayType=null&__external=false&__fileMimeType=null&__fileName=null&__fileSize=null&__mediaTraceId=null&url=null)
### **3.2 Key Metrics and Calculations**

#### **Effective Discount Percentage**

* **Definition:** Calculated as the **average of all discount points** across the selected product, store, and date filters.
* This is a **non-editable field**.

#### **Discount Value %**

* **Definition:** Rounded to the nearest multiple of **5**, as the backend table considers **20 scenarios** with a gap of 5 units.
* **Example:** If the effective discount percentage is **53.12%**, it is rounded up to **55%.**
* Editable for **future weeks**.
* Non-editable for **historical weeks**.

#### **Last year Discount %**

* This shows the **average of all discount points** across the selected product, store, and date filters for the **last year**.

#### **Actual Discount %**

* This shows the **average of the current applied discount points** for the **current year**.

### **3.3 Impact of Changing Fields**

#### **Changing Discount Value %**

* **At the Column Level:**  
  Changing the **Discount Value %** in the column applies the value to **all weeks** visible on the screen.

    * **Example:** Setting the **Discount Value %** to **20** updates it for all weeks.
    
* **At the Week Level:**  
  Changing the **Discount Value %** for a specific week will:

    * Update the **Adjusted IA Forecast** value.
    * Update the **Adjusted User Forecast** value, as it depends on the Adjusted IA Forecast and its multiplier.
    

#### **Backend Table Details**

* **Table Name:**  
  `{project_id}.{dataset_name}.ada_visual_predictions`
* **Columns Used:**

    * `default_discount_flag`: Indicates the row for **IA original forecast units**.(Will not change with user made changes on the application. Always retains the discount scenario used to predict the IA original forecast)
    * `adjusted_discount_flag`: Indicates the row for **IA adjusted forecast units**. (By default, value will be **true** only for the default discount point scenario & other scenarios are **false**. However, if a user changes the Discount % from the application and saves, value will be updated to **true** for that scenario.)
    * For every Store-SKU week combination on the backend table scenario, only **one row**(scenario) has a value of **“true”**, while the other 19 rows will be **“false”**

### **5.1 Forecast Summary Table – Row Header Descriptions**

* **Original IA Forecast**:  
  Forecast generated by the ADA team based on pricing and demand, considering various client-specific parameters.

    * Example: For a specific SKU, the ADA team may account for seasonality, location, and promotions.
    
* **Adjusted IA Forecast**:  
  Updated forecast after **Discount % changes** made by the user in the **"Drivers of Forecast"** table.
* **Adjusted User Forecast**:

### **ADA Visual MFP Forecast Split**

#### **How is the MFP forecast split?**

* **Table 1:** `ada_visual_predictions` → Aggregates forecast units at article (Style-Color or choice), channel, fiscal year week, and promo percentage level.
* **Table 2:** Subquery from `mfp_master` → Aggregates MFP units at article (Style-Color or choice), channel, and fiscal year week level.

#### **Join Conditions & Filters**

* Joins on `article`, `channel`, and `fiscal_year_week`.
* Includes only rows where `mfp_units (article, channel, week) > 0`.
* `ada_visual_mfp_forecast_split` contains **MFP units** & **IA forecast** aggregated at **article, channel, fiscal year week, and promo percentage level**.

---

### **Client Forecast Update in ADA Visual Predictions Table**

1. **Calculate values at article, channel, week, and promo percentage level:**

    * `split_ratio = mfp_units / forecast_units`
    * `product_store_count` = Count of distinct product-store combinations.
    * `splitted_mfp_units = mfp_units / product_store_count`.
    * `ia_forecast = SUM(predicted_qty)`.
    
2. **Update ADA Visual Predictions Table at product, store, week, and promo percentage levels:**

    * **client_forecast** =
    
        ```
        CASE WHEN b.ia_forecast = 0 
        THEN b.splitted_mfp_units ELSE b.split_ratio * a.predicted_qty_round
        ```

Adjusted User Forecast can be changed by two ways :

* By directly editing forecasts in the **View/Edit Hierarchy** tab.

* IA retains the Adjusted User Forecast & Discount % after the forecast refresh.
* Due to this, the Multiplier to be recalculated using the formula:

Alternatively, IA can retain the multiplier during the forecast refresh instead of the Adjusted User Forecast. As a result, after the refresh, the Adjusted User Forecast will be calculated as:

**Adjusted User Forecast = Adjusted IA Forecast × Multiplier**

This is a significant change as it impacts the DB and requires updates to the refresh sync SPs.

# Backend Tables Overview

It's essential to understand the backend BigQuery tables that powers the tool. These tables serve as the data source for the frontend, enabling calculations, back-sync processes, and overall data presentation within the tool.

## **ADA Visual Predictions Tables**

### **1. ADA Visual Predictions (**`ada_visual_predictions`**)**

* This table is **future-focused** and covers data from the first fiscal day of the current week through the simulation time period.
* Data is stored at the **SKU-Store-Week-Scenario** level.

### **2. ADA Visual Predictions Updated View (**`ada_visual_predictions_updated`**)**

* This view combines **store and product hierarchy** with data from the `ada_visual_predictions` table.
* It is consumed directly as a **backend** for the ADA Visual screen.

### **3. ADA Visual Predictions History (**`ada_visual_predictions_hist`**)**

* Stores **snapshots of forecasts**, capturing an **8-week window** every week.
* Typically stores **8 snapshots**, but configuration can be adjusted per client requirements.
* When a 9th snapshot is created, the **oldest snapshot is deleted** to manage cost and storage.
* Data is stored at the **SKU-Store-Week-Scenario-Snapshot Week** level.
* Only two scenarios are maintained:

    1. **IA Recommended Scenario**
    2. **Final User-Adjusted Scenario**
    

### **4. ADA Visual Actuals (**`ada_visual_actuals`**)**

* Aggregates **transaction data** at the **Store-SKU-Week** level.
* There are **no storage limits**, and transaction data is appended continuously.

### **5. ADA Visual Calendar (**`ada_visual_fiscal_date_mapping_graph`**)**

* This table controls the dates shown on the tables and charts in the ADA Visual module.
* This is a one time update for every client. It uses the fiscal_year_mapping table. 
* This needs to be updated if there has been a change in fiscal_year_mapping table from the sourcing side.

| --- | --- |
| **Table Update** | The table is updated on first day of every fiscal year week.  It retains the **last 8 weekly snapshots** from the current week.  Any snapshot older than **8 weeks** is automatically deleted. |
| **Example** | If the current week is **202502**, the update will retain snapshots from **202446 onwards**, deleting **202445**. |
| **Latest Snapshot Source** | The latest snapshot is always fetched from `ada_visual_predictions`. |

##### **Populating the ADA Visual Historical Dropdown**

| **Section** | **Details** |
| --- | --- |
| **Table Name** | `ada_visual_historical_dropdown` |
| **Functionality** | Controls which **historical fiscal year-week snapshot** is used when a user selects a value from the **"See Historical View"** dropdown in the tool. |
| **Columns** | `snapshot_week`  `hist_week_values`  `available_hist_weeks` |
| **How It Works** | When a user selects a historical range (e.g., **“5 weeks”**), the system queries this table to find the corresponding **snapshot week** (e.g., **202450**).  The system then retrieves historical data from `ada_visual_predictions_hist`, joining on `snapshot_week`, and populates the tool with the relevant data. |

##### **Logic to Determine Snapshot Week**

| **Scenario** | **Calculation** | **Result** |
| --- | --- | --- |
| **Case 1: Within the Same Year** | If the current week is **202452** and we need **202448**:   
**202452 - 202448 = 4** | **4th-week snapshot** |
| **Case 2: Crossing Into the Next Year** | If the current week is **202502** and we need **202448**:   
**202502 - 202448 = 54** (exceeds 8 weeks)   
To adjust for year transition, subtract **48 weeks** (weeks in a year):   
**54 - 48 = 6** | **6th-week snapshot** |

### **Daily/Weekly Refresh**

Daily Refresh can be considered if there is daily fluctuation in the below tables:

* **Product Store Eligibility**  
  If we see a lot of new SKU-Store combinations being added/removed mid-week, then it makes sense to set up a daily refresh for such clients.
* **Supersession**  
  If we see that supersession activates mid-week or is introduced in master data frequently, then a daily refresh will help keep forecasts relevant.
* **Product Master**  
  If we see a lot of new SKUs being added in the Product Master mid-week and we need to allocate immediately, then a daily refresh can be considered.

**If the above-mentioned data feeds are not volatile, then a weekly refresh should suffice.**

#### **Adjusted Forecast Screen – FAQs**

#### **1. What drivers are displayed on the screen? Is this configurable?**

* By default, the tool displays **“Discount Value %”** and **“Effective Discount %”** as forecast drivers.
* **Discount Value %** influences the **IA Forecast Value**.
* The drivers shown on this screen are **configurable** based on client requirements. Additional drivers can be included as needed.

#### **2. Are the number of weeks displayed based on the date range selected in filters? What happens if forecast data is missing for some weeks?**

* Yes, the number of weeks shown on the **Adjusted Forecast** screen is determined by the **date range selected** in the filters.
* The tool can display a **maximum of 26 weeks**.
* If a user selects a week where forecast data is **not available**, the fields for that week will appear **blank and non-editable**.

#### **3. Why is the Effective Discount % not editable? From which table is this value populated?**

* The **Effective Discount %** is derived as the **average of promo percentages** for the selected product hierarchy **when the adjusted discount flag is set to "true."**
* It can be aggregated at a **weekly level** or at an **overall level** for the selected hierarchy.
* Effective Discount % is **not necessarily a multiple of 5**, but IA rounds it to the **nearest multiple of 5** for calculating the **Adjusted IA Forecast**.
* This data is populated from the **BigQuery table:** `ada_visual_predictions`.

#### **4. How is the overall Effective Discount % calculated from weekly values?**

* The **overall Effective Discount %** is computed as the **average of the Effective Discount % across all selected weeks** in the date range.
* This value is then **rounded to the nearest multiple of 5%** to determine the **final overall discount value**.

#### **5. Can there be a case where Effective Discount % > Discount %?**

* Yes, this is possible.
* Example:

    * If the **Effective Discount %** is **42.2%**, the Discount % would be rounded to **40%**.
    * If the **Effective Discount %** is **43.2%**, the Discount % would be rounded to **45%**.
    

#### **6. If the user edits the overall Discount %, how does it affect individual weekly values?**

* If the user **updates the overall Discount % (e.g., to 40%)**, then **all individual weekly values** within the selected range will be updated to **40%**.

#### **7. If a user changes the Discount % for a specific week, how does it impact the system (frontend & backend)?**

##### **Backend Changes:**

* Example: If a user updates the **Discount % from 20% to 40%** for a specific week:

    * **Before the change:**
    
        * `default_discount_flag = 1`
        * `adjusted_discount_flag = 1`
        * Original and Adjusted IA Forecast values are the same.
        
    * **After the change:**
    
        * `default_discount_flag = 1` (remains the same)
        * `adjusted_discount_flag = 0` for 20% and **1 for 40%**
        * The new **Adjusted IA Forecast** is calculated based on **40% discount**.
        
    * Since the **BigQuery table (**`ada_visual_predictions`**)** is structured at the **product_code, store_code, and fiscal_year_week level**, changes are updated at the **product level** and then aggregated for weekly/monthly/quarterly reporting.
    

##### **Frontend Changes:**

* The **Original IA Forecast** remains unchanged.
* The **Adjusted IA Forecast** is **updated** based on the backend calculations.
* The **Adjusted User Forecast** also changes, as it is computed as: 

    Adjusted User Forecast = Multiplier × Adjusted IA Forecast


* These updates are **reflected on the Visualization screen**.
* Changes at **higher levels** (e.g., overall product level) will also **impact lower-level views**, including:

    * **Choice Level**
    * **SKU Level**
    * **Store Level**
    
* These changes can be viewed in the **"View/Edit Hierarchy Forecasts"** screen.

#### **8. Which tables store these values? Are there separate tables for granular vs. overall data?**

* **All forecast adjustments** are stored in a **single table:** `ada_visual_predictions`.
* The table **"ada_visual_predictions"** is sufficient to handle all lower-level and higher-level forecast aggregations shown in the tool.

#### **Forecast Deep Dive – FAQs**

### **1. Where do these forecast metrics come from?**

* **Original IA Forecast:** This metric is populated from the `"predicted_qty"` column in the `"ada_visual_predictions"` table, considering only rows where `"default_discount_flag"` is `true`.
* **Adjusted IA Forecast:** This metric is sourced from the `"predicted_qty"` column in the `"ada_visual_predictions"` table, using rows where `"adjusted_discount_flag"` is `true`.
* **Multiplier:** The multiplier is calculated dynamically using the formula:  
  _Multiplier = Adjusted Forecast Qty / Predicted Qty_.  
  It is not stored in any backend table.
* **Adjusted User Forecast:** This metric comes from the `"adjusted_forecast_qty"` column in the `"ada_visual_predictions"` table, filtered where `"adjusted_discount_flag"` is `true`.
* **MFP:** The MFP values are sourced from the Client-sent MFP feed. Within the `"ada_visual_predictions"` table, the `"client_forecast"` column is used to populate this metric.
* **Actuals (Actual, Last Year Actuals, Last to Last Year Actuals):** These historical actuals are retrieved from the `"ada_visual_actuals"` table by filtering for the relevant historical weeks.

### **2. Where do these metrics get back-synced?**

* **Multiplier:** This value is not retained in the backend. Instead, it is recalculated dynamically as _adjusted_forecast_qty / predicted_qty_.
* **Adjusted User Forecast:** This metric is back-synced to the `"ada_visual_predictions"` table in the `"adjusted_forecast_qty"` column.

#### **Backend Tables – Simplified FAQs**

#### **ADA Visual Actuals Table Update**

#### **How are tables joined?**

* **transaction_master** → LEFT JOIN **supersession_master** (on `product_code = sub_product_code`) → Replaces old product codes with `main_product_code`.
* **fiscal_date_mapping** → LEFT JOIN (using `date`) → Adds fiscal calendar details (week, month, quarter, year).
* **product_master** → INNER JOIN (using `product_code`) → Adds product details (`product_bucket_code`).
* **store_master** → LEFT JOIN (using `store_code`) → Adds store details.

#### **What filters are applied?**

* **transaction_master**: Only includes transactions where:

    * `qty > 0` (positive quantities only).
    * `total_discount_amount >= 0` (non-negative discounts).
    * Date range: Last 24 months up to the previous week.
    
* **product_master**: Excludes rows where `product_code IS NULL`.

#### **How are actuals updated in the tool?**

* **Tables used:**

    * `ada_visual_actuals_updated` (a view table) → Uses the above joins.
    * `ada_visual_product_store_mapping` → Contains eligible product-store combinations from `ADA Visual Predictions`.
    
* **Joins applied:**

    * INNER JOIN on `product_code` & `store_code`.
    * If "All SKUs" is selected, the join with `ada_visual_product_store_mapping` is skipped, and all SKUs from `ada_visual_actuals_updated` are included.
    
* **Data rules:**

    * **Historic weeks:** Both Actuals and Last Year Actuals have values if transactions exist.
    * **Future weeks:** Actuals are blank, but Last Year Actuals have values if transactions existed in the same week last year.
    

---

#### **ADA Visual Predictions Table Update**

#### **How are tables joined?**

* **ada_sim_out_active** (ADA simulation output) joins with:

    * `product_master` (on `product_code`).
    * `store_master` (on `store_code`).
    * `fiscal_date_mapping` (on `fiscal_year_week`).
    * `discount_selection` (on `product_code`, `store_code`, `fiscal_year_week`).
    
* No explicit filters are applied.

#### **How are Historic Forecasts & MFP handled?**

* **"All SKUs" Toggle** → Historic forecasts & MFP are based on historical SSEs.
* **"Eligible SKUs" Toggle** → Uses current & forward-looking SSEs. Only products eligible in both current & past weeks are considered for aggregation.
* **Impact of toggle selection:**

    * Affects Actuals, Forecast, and MFP metrics.
    * If the user selects 6 historic weeks, `ADA_VISUAL_PREDICTIONS_HIST` is filtered for `snapshot_week` of the 6th week in the past.
    

**Example:**

* If `previous_week = 202443`, the 6th week in the past is `202438`.
* Forecasts for **weeks 202438 to 202443** will be shown for `snapshot_week = 202438`.
